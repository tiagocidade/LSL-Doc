# Estrutura de Scripts LSL no Second Life

**A Estrutura Fundamental da Linden Scripting Language (LSL) no Second Life**

**1. Introdução à Linden Scripting Language (LSL)**

A Linden Scripting Language (LSL) é a linguagem de programação proprietária utilizada no ambiente virtual Second Life (SL).1 Desenvolvida pela Linden Lab, a LSL permite que os residentes (usuários) do Second Life adicionem comportamentos e interatividade aos objetos tridimensionais, conhecidos como primitivas (prims), que constituem os blocos de construção básicos do mundo virtual.2 Sem scripts, os objetos em SL são estáticos e não interativos.3 Com LSL, é possível fazer objetos se moverem, mudarem de aparência (cor, tamanho, textura), comunicarem-se via chat, responderem a toques ou comandos de voz, operarem como veículos, detectarem avatares próximos, interagirem com serviços web externos e muito mais.2

A LSL é uma linguagem orientada a eventos e baseada em estados, com uma sintaxe inspirada em linguagens como C e Java.1 Os scripts LSL são escritos, compilados e gerenciados através de um editor embutido no cliente oficial do Second Life (Viewer) ou em visualizadores de terceiros.2 No entanto, a execução dos scripts ocorre nos servidores do Second Life (simuladores ou "sims"), não no cliente do usuário.2 O servidor processa o script e envia os resultados (como movimento de objetos, mensagens de chat, etc.) para os visualizadores dos usuários conectados.2 Objetos com scripts podem ser anexados aos avatares, permitindo a criação de HUDs (Heads-Up Displays), acessórios animados, entre outros.2

**2. A Estrutura Central: Estados e Eventos**

A característica distintiva da LSL é sua forte ênfase em **estados** e **eventos**.2 Essa abordagem permite modelar comportamentos complexos de forma organizada.

● **Estados (States)**

○ Um estado representa uma condição ou modo de operação específico de um script. Por exemplo, uma porta pode estar no estado "aberta" ou "fechada", uma luz no estado "ligada" ou "desligada".2

○ Em qualquer momento, um script está em um único estado ativo.9

○ Todo script LSL **deve** conter pelo menos um estado, chamado estado default.2 Este é o estado inicial quando o script começa a rodar ou é

resetado.10

○ Estados adicionais podem ser definidos pelo programador usando a

palavra-chave state seguida pelo nome do estado e um bloco de código entre chaves {}.8 Por exemplo: state ligado {... }.

○ A definição do estado default é especial e não requer a palavra-chave state antes dela; apenas default {... } é usado.8 O estado default deve ser o primeiro estado definido no script.10

○ A transição entre estados é realizada usando o comando state

nome_do_estado;.9 Quando uma mudança de estado ocorre, várias ações são executadas:

1. O evento state_exit() do estado atual (se definido) é executado.9

2. A fila de eventos pendentes do script é limpa.9

3. Muitos eventos que requerem configuração prévia (como listen e sensor) são desativados/resetados.9 Notavelmente, o evento timer persiste através das mudanças de estado.5

4. O script entra no novo estado.

5. O evento state_entry() do novo estado (se definido) é executado.9 ○ O uso de estados pode simplificar a lógica do script, tornando o fluxo de controle mais linear em comparação com o uso extensivo de variáveis globais e condicionais if para rastrear o estado.11

● **Eventos (Events) e Manipuladores de Eventos (Event Handlers)**

○ Eventos são gatilhos predefinidos no sistema Second Life que sinalizam a ocorrência de alguma ação ou mudança no ambiente.2 Eles podem ser causados por interações de avatares (como tocar um objeto), interações entre objetos (colisões), ações internas do script (como llRezObject

disparando object_rez), ou condições de tempo (como o timer). Os eventos não são definidos pelo usuário.2

○ Para cada evento que um script precisa responder dentro de um estado específico, um **manipulador de eventos** (event handler) correspondente deve ser definido.2 Um manipulador de eventos é um bloco de código nomeado (ex: touch_start(), state_entry()) que é executado quando o evento correspondente ocorre.

○ A estrutura básica de um manipulador de evento é

nome_do_evento(parametros) { /* código a ser executado */ }.2 Mesmo que um manipulador não execute nenhuma ação, ele deve ser definido com chaves vazias {}.8

○ Quando um evento ocorre para o qual um manipulador está definido no estado atual do script, o evento é colocado em uma **fila de eventos**.9

○ O simulador processa essa fila em ordem FIFO (First-In, First-Out),

executando um manipulador de eventos por vez.16 Eventos **não podem** interromper a execução de outro evento que já esteja rodando; o manipulador atual deve terminar antes que o próximo da fila possa começar.13

○ A fila de eventos tem um tamanho limitado (mencionado como 64 ou 300 em

diferentes fontes/contextos, mas a ideia de um limite existe).13 Se a fila estiver cheia, novos eventos são descartados.16

○ Todo script LSL deve ter pelo menos um estado (o default) contendo pelo menos um manipulador de eventos.2 O manipulador state_entry() é

frequentemente usado para inicialização.2

● Estrutura Mínima e Exemplo Básico

O script LSL mais simples e válido contém apenas o estado default e um

manipulador de eventos state_entry vazio 8:

Snippet de código

default

{

state_entry()

{

// Nenhuma ação aqui

}

}

Um exemplo mais funcional, frequentemente fornecido como template inicial, é o script "Hello, Avatar!" 2:

Snippet de código

default // Define o estado padrão obrigatório

{

// Evento executado uma vez quando o script entra neste estado

state_entry()

{

llSay(0, "Hello, Avatar!"); // Faz o objeto dizer "Hello, Avatar!" no chat público (canal 0)

}

// Evento executado quando um avatar clica (toca) no objeto

touch_start(integer total_number) // total_number informa quantos avatares estão tocando

{

llSay(0, "Touched."); // Faz o objeto dizer "Touched." no chat público }

}

Neste exemplo:

1. Ao ser salvo ou resetado, o script entra no estado default.

2. O evento state_entry() é disparado, e o objeto diz "Hello, Avatar!".

3. O script então fica ocioso, esperando por outros eventos.

4. Se um avatar clicar no objeto, o evento touch_start() é disparado, e o objeto diz "Touched.".

**3. Sintaxe Essencial da LSL**

A sintaxe da LSL, embora descrita como "simples" por programadores experientes (indicando limitações em comparação com linguagens mais complexas), requer precisão absoluta.4 Qualquer erro de ortografia, pontuação ou estrutura resultará em erro de compilação ou comportamento inesperado.4 A sintaxe é fortemente baseada em C e Java.1

● **Declaração de Variáveis e Tipos de Dados**

○ Variáveis são nomes usados para armazenar informações (valores) dentro de um script.4 Elas devem ser declaradas antes de serem usadas, especificando seu tipo e nome.29 A declaração pode incluir uma inicialização opcional.4 ○ Formato: tipo nome_da_variavel; ou tipo nome_da_variavel = valor_inicial;.29 ○ Nomes de variáveis podem conter letras (maiúsculas/minúsculas), números e underscores (_), mas não podem começar com um número.30 Há um limite prático de 255 caracteres para nomes de variáveis.30

○ Escopo: Variáveis podem ser globais (declaradas fora de qualquer estado ou função, acessíveis em todo o script) ou locais (declaradas dentro de um evento ou função, acessíveis apenas nesse bloco).4

○ Tipos de Dados Fundamentais LSL 5:

■ integer: Números inteiros de 32 bits com sinal.5 Exemplos: 42, -10, 0.

Usado para contagens, flags, canais, etc. TRUE é representado como 1 e FALSE como 0.27

■ float: Números de ponto flutuante (decimais) de 32 bits com sinal.

Exemplos: 3.14, -0.01, 1.0. Usado para posições, tempos, porcentagens.

■ string: Sequências de caracteres alfanuméricos, delimitadas por aspas duplas ".27 Exemplos: "Hello, world!", "My Texture", "" (string vazia). Usado para nomes, mensagens, UUIDs (embora key seja preferível para UUIDs).

O comprimento máximo pode variar dependendo do contexto e do motor de script.5

■ key: Um Identificador Único Universal (UUID) de 128 bits, representado como uma string de 36 caracteres hexadecimais com hífens.27 Exemplo: "f1a1b2c3-d4e5-f6a7-b8c9-d0e1f2a3b4c5". Usado para identificar avatares, objetos, texturas, etc. NULL_KEY

("00000000-0000-0000-0000-000000000000") é uma constante

chave especial.

■ vector: Uma estrutura contendo três valores float, representando um ponto ou direção no espaço 3D.5 Delimitado por < e >. Exemplo: <1.0, 2.5, -3.0>. Usado para posições, cores (RGB), velocidades, escalas.

■ rotation: Uma estrutura contendo quatro valores float, representando uma orientação (rotação) no espaço 3D usando um quaternion.5 Delimitado por < e >. Exemplo: <0.0, 0.0, 0.0, 1.0> (rotação nula). Usado para orientar objetos.

■ list: Uma coleção ordenada de zero ou mais valores de qualquer tipo LSL (incluindo outras listas).5 Delimitada por colchetes ``. Exemplo: [1, "hello", <1,0,0>, NULL_KEY]. Listas são muito versáteis, mas operações como concatenação podem ter implicações de performance, especialmente no motor LSO.5

● **Operadores**

○ LSL fornece um conjunto de operadores para realizar operações aritméticas, lógicas, de comparação, bitwise e de atribuição.12

○ Operadores Aritméticos: + (adição, concatenação de string/lista), -

(subtração, negação), * (multiplicação, produto escalar de vetores), /

(divisão), % (módulo para inteiros, produto vetorial para vetores).29 Divisão por zero ou módulo por zero causa erro em tempo de execução.33

○ Operadores de Comparação: == (igual a), != (diferente de), < (menor que), > (maior que), <= (menor ou igual a), >= (maior ou igual a).29 Retornam TRUE (1) ou FALSE (0). A comparação de igualdade == para listas verifica apenas o comprimento, não o conteúdo.33

○ Operadores Lógicos: && (E lógico), || (OU lógico), ! (NÃO lógico).29

**Importante:** Ao contrário de muitas linguagens C-like onde o segundo operando pode não ser avaliado (curto-circuito), em LSL *ambos* os

operandos de && e || são *sempre* avaliados.33 Isso exige cautela ao escrever condições que dependem da avaliação do primeiro operando para a

segurança do segundo (ex: verificar se um divisor é diferente de zero antes de usá-lo). Tais casos podem exigir ifs aninhados.

○ Operadores Bitwise (para integer): & (E bitwise), | (OU bitwise), ^ (XOR bitwise), ~ (NÃO bitwise), << (deslocamento à esquerda), >> (deslocamento à direita).13

○ Operadores de Atribuição: = (atribuição simples), +=, -=, *=, /=, %= (atribuição composta).13

○ Outros: () (agrupamento), `` (construção de lista), (tipo) (typecasting).33 ○ Precedência e Associatividade: Operadores têm uma ordem definida de avaliação (precedência) e regras para agrupar operadores de mesma

precedência (associatividade).29 Parênteses () podem ser usados para forçar uma ordem de avaliação específica.33 A maioria dos operadores é associativa à esquerda, mas os lógicos (&&, ||) e de atribuição são associativos à direita.33 ● **Estruturas de Controle de Fluxo**

○ Permitem alterar a ordem sequencial de execução do código com base em condições ou repetições.12

○ Condicional: if (condição) {... } else {... }.11 Executa um bloco se a condição for TRUE, e opcionalmente outro (else) se for FALSE.

○ Loops (Laços de Repetição):

■ while (condição) {... } 12: Repete o bloco enquanto a condição for TRUE. Testa *antes* de cada iteração.

■ do {... } while (condição); 12: Similar ao while, mas testa *depois* de cada iteração, garantindo pelo menos uma execução.

■ for (inicialização; condição; incremento) {... } 12: Loop controlado por contador. Executa inicialização uma vez, repete o bloco e incremento enquanto condição for TRUE.

○ Controle de Estado: state nome_do_estado; (discutido anteriormente).9 ○ Salto: jump nome_label; e @nome_label;.5 Permite saltar para um ponto (label) dentro do *mesmo* manipulador de eventos ou função. Seu uso é geralmente desencorajado por dificultar a leitura e manutenção do código. O motor LSO tinha comportamentos inesperados com jump.5

○ Retorno: return valor;.12 Usado dentro de funções para sair e opcionalmente retornar um valor. Manipuladores de eventos LSL padrão são void (não retornam valor).

○ A natureza orientada a eventos e estados da LSL frequentemente favorece o uso de múltiplos estados ou eventos (como timer) para gerenciar o fluxo lógico ao longo do tempo, em vez de depender de loops complexos ou jumps dentro de um único manipulador de eventos, especialmente porque

manipuladores de eventos devem ser rápidos para evitar impacto na

simulação.11

● **Funções: Embutidas (ll*) e Definidas pelo Usuário**

○ Funções Embutidas (ll*): Uma extensa biblioteca de funções predefinidas pela Linden Lab que formam a interface principal entre o script e o ambiente Second Life.2 Exemplos incluem llSay(), llSetColor(), llGetPos(), llListen(), llSetTimerEvent(). Seus nomes sempre começam com ll. Dominar as funções relevantes é essencial para scripting em LSL.12

○ Funções Definidas pelo Usuário: Blocos de código reutilizáveis criados pelo scripter.5 São definidas fora dos estados, especificando um tipo de retorno (ou void se não houver retorno), um nome, uma lista de parâmetros entre

parênteses (), e o corpo da função entre chaves {}.5 Exemplo: integer

soma(integer a, integer b) { return a + b; }.29 Funções definidas pelo usuário são cruciais para organizar o código, evitar repetições e melhorar a

legibilidade, especialmente em scripts maiores.36 Elas não podem mudar o estado do script diretamente usando state nome_do_estado; (embora existam workarounds com if, cujo uso é desencorajado por depender de um possível bug/feature não garantido).10 Esta restrição reforça o papel central dos manipuladores de eventos como os pontos onde o controle de estado deve ocorrer.

○ Chamada de Função: Para executar uma função, usa-se seu nome seguido de parênteses (), passando os argumentos necessários.29

● **Comentários (//) e Formatação**

○ Comentários: Texto explicativo ignorado pelo compilador. Comentários de linha única começam com //.4

○ Formatação: Embora espaços em branco (espaços, tabulações, novas linhas) sejam flexíveis para o compilador, o uso consistente de indentação e o alinhamento vertical de chaves {} são fundamentais para a legibilidade e manutenção do código por humanos.8 Ferramentas externas podem auxiliar na formatação automática.27

**4. Eventos Principais em Ação**

Embora LSL ofereça muitos eventos 12, alguns são particularmente fundamentais para a maioria dos scripts interativos.

● **Eventos de Inicialização e Transição: state_entry() e state_exit()**

○ state_entry(): Disparado automaticamente sempre que o script entra em um estado, seja no início da execução (no estado default) ou após uma transição de estado via state.2 É ideal para inicializar variáveis, configurar listeners ou timers, ou realizar qualquer ação que deva ocorrer imediatamente ao entrar no estado. Não recebe parâmetros. É importante notar que state_entry **não** é disparado quando um objeto é rezado (colocado no mundo) a partir do inventário se o script já estava em um estado salvo; para isso, o evento on_rez() deve ser usado.5 Uma prática comum para código de inicialização que precisa rodar tanto no início quanto ao rezar é colocá-lo em uma função definida pelo usuário e chamá-la de ambos state_entry() e on_rez().11

○ state_exit(): Disparado imediatamente *antes* de o script sair do estado atual devido a um comando state.9 É útil para realizar tarefas de limpeza antes da transição, como remover listeners, parar timers (embora persistam por padrão), ou salvar dados. Não recebe parâmetros. Não é disparado quando o

objeto é deletado.14

● **Interação por Toque: touch_start(), touch(), touch_end()**

○ Estes eventos respondem ao clique do mouse de um avatar sobre o objeto que contém o script (não a colisões físicas).2

○ touch_start(integer num_detected): Disparado no instante em que o clique começa.2 num_detected indica quantos avatares estão tocando. Funções llDetected*() (ex: llDetectedKey(0), llDetectedName(0)) podem ser usadas dentro deste handler para obter informações sobre quem tocou.40

○ touch(integer num_detected): Disparado repetidamente enquanto o botão do mouse é mantido pressionado.16

○ touch_end(integer num_detected): Disparado no momento em que o botão do mouse é liberado.8

○ Considerações Importantes:

■ Múltiplos Eventos por Clique: Devido a fatores como drivers de mouse, é possível receber múltiplos eventos touch_start ou touch_end para um único clique físico.40 Scripts sensíveis a cliques únicos podem precisar implementar lógica de "debouncing".

■ Mudança de Estado: É uma prática fortemente recomendada realizar mudanças de estado (state...;) dentro do touch_end em vez do

touch_start. Fazer isso no touch_start pode levar a comportamentos inesperados, como eventos sendo perdidos ou disparados novamente no novo estado se o botão do mouse ainda estiver pressionado.10

■ Prim Drift: Clicar em um objeto pode acidentalmente movê-lo se o usuário arrastar o mouse ligeiramente. Isso pode ser evitado usando

llSetStatus(STATUS_BLOCK_GRAB, TRUE); no script.40

■ Objetos Vinculados (Linksets): O comportamento do toque em objetos com múltiplos prims depende de quais prims (raiz ou filhos) contêm manipuladores de toque. A função llPassTouches() pode ser usada para controlar como os eventos de toque são passados entre prims filhos e o prim raiz.42

● **Comunicação por Chat: listen() (requer llListen())**

○ Permite que um script reaja a mensagens de chat ditas por avatares ou outros objetos.13

○ Ativação e Filtragem: O evento listen só é disparado se um "ouvinte" (listener) foi previamente ativado usando a função llListen(integer channel, string name, key id, string msg). Esta função define os critérios (canal, nome do falante, key do falante, conteúdo da mensagem) que uma mensagem de chat deve atender para disparar o evento.14 Usar filtros restritivos é crucial para a performance.19 llListen retorna um handle (identificador inteiro) que pode ser

usado com llListenRemove() para desativar o ouvinte.14

○ Manipulador: listen(integer channel, string name, key id, string message) recebe os detalhes da mensagem ouvida.14

○ Canais: O canal 0 é o chat público local. Outros canais inteiros (positivos e negativos) são privados e usados para comunicação entre scripts.28

DEBUG_CHANNEL é um canal especial para mensagens de depuração.19 ○ Considerações Importantes:

■ Performance: Ouvintes abertos (sem filtros ou com filtros muito amplos) no canal 0 podem causar lag considerável no simulador, pois cada mensagem de chat na área precisa ser processada pelo script.28 É preferível usar canais privados e filtros específicos sempre que possível.

■ Limpeza Automática: Listeners são automaticamente removidos quando o script muda de estado ou é resetado.9 Portanto, llListen() geralmente precisa ser chamado novamente no state_entry() de cada estado que precisa ouvir chat.

■ Localização: O ponto de "escuta" está na posição do prim raiz do objeto, não necessariamente no prim que contém o script.20

■ Limite: Existe um limite para o número de listeners ativos por script (mencionado como 65).19

● **Ações Temporizadas: timer() (requer llSetTimerEvent())**

○ Permite executar código em intervalos regulares.5

○ Ativação/Desativação: A função llSetTimerEvent(float sec) configura o evento timer() para ser disparado aproximadamente a cada sec segundos. Um valor de 0.0 desativa o timer.22

○ Manipulador: timer() não recebe parâmetros.

○ Comportamento Único:

■ Persistência entre Estados: Ao contrário de listen e sensor, o timer **continua funcionando** mesmo após uma mudança de estado.5 Se o novo estado tiver um manipulador timer(), ele será executado no intervalo definido anteriormente. Isso requer gerenciamento cuidadoso; é boa prática desativar o timer explicitamente (llSetTimerEvent(0.0);) no state_exit() do estado antigo ou no state_entry() do novo estado, se ele não for mais necessário.22

■ Substituição: Chamar llSetTimerEvent() novamente substitui qualquer configuração de timer anterior e reinicia o relógio.22

■ Atraso Inicial: O primeiro evento timer() ocorre somente *após* o primeiro intervalo ter decorrido.31

■ Precisão: O intervalo real pode variar devido ao lag do simulador (time dilation), carga de scripts e eventos, ou execução prolongada de outros

manipuladores de eventos.22 Não é adequado para temporização de alta precisão.

● **Detectando Mudanças no Objeto: changed()**

○ Disparado quando certas propriedades do objeto ou de seus prims

constituintes são modificadas externamente (por um usuário ou pelo

sistema).13

○ Manipulador: changed(integer change) recebe um parâmetro change que é um campo de bits (bit field). Cada bit representa um tipo específico de mudança.35

○ Flags de Mudança (CHANGED_*): Indicam o que mudou, como inventário (CHANGED_INVENTORY), cor (CHANGED_COLOR), forma (CHANGED_SHAPE), escala (CHANGED_SCALE), textura (CHANGED_TEXTURE), número de links ou avatares sentados (CHANGED_LINK), adição de inventário permitida

(CHANGED_ALLOWED_DROP), mudança de proprietário (CHANGED_OWNER), mudança de região (CHANGED_REGION), teleporte do avatar anexado (CHANGED_TELEPORT), etc..35

○ Verificação: É essencial usar o operador bitwise AND (&) para verificar quais flags estão presentes no parâmetro change, pois múltiplas mudanças podem ser reportadas em um único evento. Exemplo: if (change & CHANGED_LINK) {... }.35 Usar == é incorreto e pode falhar em detectar mudanças se mais de uma ocorrer simultaneamente.35

○ Limitações: Muitas alterações comuns **não** disparam o evento changed, incluindo mudanças de posição ou rotação (requerem

moving_start/moving_end ou polling com timer), alterações no

nome/descrição, permissões de objeto, flags de física/fantasma, llSetText, anexar/desanexar (requer attach), entre outras.35

**5. Compilação e Inserção de Scripts em Objetos**

Para que um script LSL se torne ativo no Second Life, ele precisa ser compilado e inserido no inventário de um objeto (prim).

● **O Editor de Scripts Embutido e Alternativas**

○ O método padrão para criar e editar scripts LSL é através do editor embutido no visualizador do Second Life.2 Este editor é acessado criando um "New Script" dentro da aba "Content" (Conteúdo) de um objeto em modo de edição, ou criando um novo script diretamente no inventário do avatar.25 ○ O editor embutido oferece recursos básicos como coloração de sintaxe (destacando palavras-chave, funções e eventos LSL), dicas sobre

palavras-chave ao passar o mouse sobre elas, e verificação básica de erros de sintaxe antes de salvar.2

○ Muitos scripters preferem usar editores de texto externos (offline) que oferecem recursos mais avançados, como melhor realce de sintaxe,

autocompletar, formatação de código, e até mesmo compilação e depuração offline (como o LSL-Editor).2 O código escrito externamente é então copiado e colado no editor embutido do SL para compilação e salvamento.2

● **O Processo de Compilação: LSL para Bytecode (LSO/Mono/SLua)**

○ Quando o botão "Save" (Salvar) é pressionado no editor LSL, o código-fonte LSL é enviado para os servidores do Second Life.2

○ No servidor, o código LSL é **compilado**, ou seja, traduzido de um formato legível por humanos para um formato de baixo nível chamado **bytecode**, que pode ser executado por uma máquina virtual (scripting engine).7

○ Este bytecode compilado é então armazenado nos servidores de assets da

Linden Lab, associado a um UUID único.7

○ Quando um objeto contendo esse script é rezado no mundo virtual, o simulador da região onde o objeto se encontra carrega o bytecode

correspondente e o executa usando um dos motores de script disponíveis.2 ○ **Motores de Execução:**

■ **LSO (LSL Scripting Optimized):** O motor original, interpretado.

Geralmente consome menos memória inicial, mas tem um limite de memória total menor (16KB) e pode ser significativamente mais lento, especialmente para operações matemáticas ou manipulação complexa de listas (onde sofre de fragmentação de memória).5

■ **Mono:** Um motor mais moderno baseado no projeto open-source Mono.

Scripts LSL podem ser compilados especificamente para Mono

(geralmente através de uma opção no editor de script).7 O bytecode Mono geralmente executa muito mais rápido que LSO.7 Ele usa alocação dinâmica de memória (mais eficiente para scripts pequenos, mas a base pode ser maior) e tem um limite de memória maior (64KB).5 Mono também suporta compartilhamento de bytecode: se múltiplas cópias do mesmo script Mono estiverem rodando na mesma região, o bytecode é carregado apenas uma vez na memória.7 É geralmente recomendado para melhor performance, mas pode introduzir diferenças sutis de timing em

comparação com LSO.7

■ **SLua (Lua):** A mais recente adição (em implantação), utiliza Lua como backend. Visa oferecer performance e eficiência de memória ainda melhores que Mono, tanto para scripts LSL (compilados para bytecode Lua) quanto para scripts escritos diretamente em Lua.51 LSL compilado para SLua tende a ter bytecode menor e usar menos memória para strings (UTF-8 vs UTF-16 do Mono).51

○ A escolha do motor de compilação (LSO vs Mono/SLua) é uma decisão importante que afeta diretamente a performance e o consumo de recursos do script no simulador. A evolução para Mono e SLua reflete os esforços

contínuos para otimizar a execução de scripts, um fator crítico para a

performance geral do Second Life.5

● **Inserindo Scripts em Objetos (Prims)**

○ O procedimento padrão para adicionar um script a um objeto é:

1. Clicar com o botão direito no objeto no mundo e selecionar "Edit"

(Editar).2

2. Na janela de edição, navegar até a aba "Content" (Conteúdo).25

3. Clicar no botão "New Script" para criar um novo script vazio (com um template padrão) dentro do objeto.25

4. Dar um duplo clique no item "New Script" recém-criado para abrir o editor LSL.25

5. Escrever ou colar o código LSL no editor e clicar em "Save" (Salvar) para compilar e salvar o script.

○ Alternativamente, um script que já existe no inventário do avatar pode ser simplesmente arrastado da janela de inventário para a aba "Content" do objeto aberto em modo de edição.52

○ Para objetos vestidos (attachments), pode ser necessário desanexar o item, rezá-lo no chão, adicionar o script via aba "Content" e, em seguida, vesti-lo novamente, especialmente se houver restrições de permissão.52 A edição direta enquanto vestido é possível se as permissões do objeto permitirem.52 ○ A capacidade de adicionar ou modificar scripts depende crucialmente das **permissões** do objeto. O objeto deve ter permissão de modificação

("Modify") para o proprietário atual.52 Objetos marcados como "no modify" não podem ter seus scripts alterados ou adicionados. As permissões do próprio script (Copy, Modify, Transfer) também são importantes,

determinando como ele pode ser compartilhado ou vendido.52

● **Considerações sobre Permissões e Prims Vinculados (Linked Prims)**

○ **Permissões:** Além da permissão "Modify" no objeto, as permissões do script (Copy/Mod/Transfer) determinam o que pode ser feito com ele. Por exemplo, um script "no copy" será removido do inventário ao ser inserido em um objeto.52 Um script "no modify" não pode ser aberto ou editado. Um script "no transfer" não pode ser dado a outro avatar (diretamente ou dentro de um objeto transferível). Entender o sistema de permissões é fundamental.52 ○ **Prims Vinculados (Linksets):** Objetos complexos em SL são frequentemente construídos vinculando múltiplos prims.2

■ **Localização do Script:** Um script pode ser colocado no inventário de qualquer prim dentro do linkset.2

■ **Prim Raiz (Root Prim):** O último prim selecionado durante o processo de vinculação torna-se o prim raiz. A localização do script (raiz vs. filho) pode afetar como certos eventos ou funções se comportam. Por exemplo, o evento listen sempre "ouve" a partir da posição do prim raiz 20, o evento changed com a flag CHANGED_SCALE só é disparado no prim raiz 48, e funções como llTargetOmega podem ter efeitos diferentes dependendo se o script está no prim raiz (rotação global do linkset) ou em um prim filho (rotação local relativa ao raiz).46

■ **Comunicação Interna:** Scripts em diferentes prims do mesmo linkset podem se comunicar de forma eficiente e privada usando mensagens de link, através das funções llMessageLinked() e do evento link_message().2

Isso é preferível a usar chat para comunicação interna.

○ Trabalhar com linksets exige atenção à estrutura do objeto. Onde colocar os scripts e como eles se comunicam são decisões de design importantes. A arquitetura de linkset "plana" do SL (sem hierarquia profunda de objetos dentro de objetos) é considerada uma limitação por alguns

desenvolvedores.54

**6. Conclusão e Próximos Passos**

A Linden Scripting Language (LSL) é uma ferramenta poderosa e essencial para criar conteúdo interativo e dinâmico no Second Life. Sua estrutura fundamental, baseada em estados e eventos, permite modelar comportamentos complexos de forma organizada. Compreender a sintaxe básica (tipos de dados, operadores, controle de fluxo), o funcionamento dos principais eventos (state_entry, touch_*, listen, timer, changed), o processo de compilação (LSO/Mono/SLua) e como inserir scripts em objetos (prims), incluindo as considerações sobre permissões e linksets, são os pilares para iniciar o desenvolvimento com LSL.

A natureza orientada a eventos e a execução no servidor exigem uma abordagem de programação que priorize a eficiência e a resposta rápida aos gatilhos do ambiente virtual. A escolha do motor de compilação (Mono ou SLua sendo preferíveis para performance) e o uso cuidadoso de recursos como listen e timer são cruciais para criar scripts que funcionem bem sem sobrecarregar o simulador.

Para aprofundar os conhecimentos em LSL, os seguintes recursos são recomendados:

● **LSL Portal na Wiki do Second Life:** É a referência definitiva e mais completa para todas as funções, eventos, tipos de dados, constantes, operadores e exemplos da linguagem.1

● **Tutoriais e Exemplos:** A Wiki do Second Life e outras fontes da comunidade oferecem numerosos tutoriais para iniciantes e uma vasta biblioteca de scripts de exemplo que podem ser estudados e adaptados.2

● **Prática Contínua:** A experimentação é fundamental. Modificar scripts existentes, tentar implementar pequenas funcionalidades e aumentar gradualmente a complexidade dos projetos são as melhores formas de solidificar o aprendizado.2 ● **Comunidade de Scripting:** Participar dos fóruns oficiais do Second Life, grupos de scripting in-world e outras comunidades online permite tirar dúvidas, trocar experiências e aprender com outros scripters mais experientes.32

Dominar a LSL abre um vasto leque de possibilidades criativas dentro do Second Life,

permitindo a construção de experiências verdadeiramente únicas e interativas.
