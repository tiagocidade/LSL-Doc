# Exemplos LSL_ Scripts Comentados Diversos_

**Compilação Comentada de Scripts LSL para Funcionalidades Comuns no Second Life**

**1. Introdução à Scripting LSL no Second Life**

**1.1. O Papel do LSL**

O Linden Scripting Language (LSL) é a linguagem de programação fundamental que confere comportamento, interatividade e funcionalidade aos objetos e avatares dentro do ambiente virtual do Second Life.1 É uma linguagem orientada a eventos, o que significa que os scripts reagem a ocorrências específicas no mundo virtual, como um toque de um avatar, uma mensagem de chat ou a passagem do tempo. Uma característica distintiva do LSL é a sua ênfase em "Estados" e "Eventos", permitindo modelar comportamentos complexos através da transição entre diferentes modos de operação (estados) em resposta a gatilhos específicos (eventos).1

**1.2. Propósito e Estrutura deste Relatório**

O objetivo deste relatório é fornecer uma coleção curada e abrangente de exemplos de scripts LSL completos, comentados e explicados, abordando tarefas comuns enfrentadas pelos criadores no Second Life. A estrutura seguirá uma progressão lógica, iniciando com scripts de deteção de presença, seguindo para sistemas de teleporte, portas interativas, controladores de luz, distribuidores de objetos (givers), sistemas de partículas e, finalmente, ouvintes de chat. Cada exemplo incluirá o código LSL completo, comentários detalhados linha a linha ou por bloco, e uma explicação aprofundada da lógica, funções utilizadas, permissões necessárias e potenciais desafios ou limitações. Concluiremos com uma lista de recursos confiáveis para estudo e consulta adicionais. É crucial enfatizar que a mera cópia de scripts sem um entendimento do seu funcionamento interno limita o potencial criativo e a capacidade de solucionar problemas.3 A prática de comentar o código abundantemente é vital não apenas para a compreensão inicial, mas também para a manutenção e

modificação futuras do script.1

**1.3. Conceitos Fundamentais de LSL**

Para facilitar a compreensão dos exemplos subsequentes, introduzimos brevemente alguns conceitos essenciais do LSL que serão recorrentes:

● **Estados:** Os scripts LSL operam dentro de "estados" definidos. Cada script possui pelo menos um estado default, mas pode ter múltiplos estados

personalizados (por exemplo, aberto, fechado, ligado, desligado). O script executa o código associado ao estado ativo e pode transitar para outros estados

em resposta a eventos.1

● **Eventos e Manipuladores de Eventos (Event Handlers):** Eventos são gatilhos predefinidos pelo sistema Second Life que ocorrem devido a interações no mundo (ex: um avatar toca um objeto) ou são iniciados por um script (ex: um temporizador expira). Quando um evento ocorre, ele aciona a execução de um bloco de código específico chamado "manipulador de eventos" (event handler), como touch_start(), listen(), sensor(), state_entry(), timer().1 state_entry() é um evento especial que dispara sempre que um script entra num novo estado.

● **Funções:** LSL oferece uma biblioteca extensa de funções incorporadas que realizam ações específicas, como enviar mensagens de chat (llSay, llOwnerSay), iniciar uma varredura de sensor (llSensor), entregar itens de inventário

(llGiveInventory), controlar parâmetros de primitivas (llSetPrimitiveParams), etc..6 Estas funções são os blocos de construção para a maioria das funcionalidades dos scripts.

● **Permissões:** Muitas ações potencialmente intrusivas ou que consomem recursos requerem permissão explícita do usuário (geralmente o proprietário do objeto ou o avatar interagindo). Exemplos incluem teleporte (PERMISSION_TELEPORT), anexar objetos ao avatar (PERMISSION_ATTACH), controlar movimentos

(PERMISSION_TAKE_CONTROLS), e permissões de cópia/transferência de itens de inventário. Scripts solicitam estas permissões usando llRequestPermissions, e a resposta do usuário é tratada no evento run_time_permissions.7 Compreender e gerir permissões é crucial para a funcionalidade e aceitação do script.

● **Tipos de Dados:** LSL utiliza vários tipos de dados para armazenar informações, incluindo integer (números inteiros), float (números de ponto flutuante), string (texto), key (identificadores únicos UUID para avatares e objetos), vector (coordenadas X, Y, Z ou cores RGB), rotation (orientação no espaço 3D), e list (coleções ordenadas de outros tipos de dados).5

**2. Scripts de Deteção de Presença e Avatar**

**2.1. Introdução à Deteção de Avatar**

A capacidade de detetar a presença de avatares nas proximidades é fundamental para uma vasta gama de aplicações interativas no Second Life, desde sistemas de segurança e portas automáticas até mecanismos de jogo e gatilhos de ambiente. Existem duas abordagens principais em LSL para realizar esta deteção: a função llSensor e a função llGetAgentList. Cada uma tem as suas próprias características, vantagens e limitações.

**2.2. Exemplo 1: Sensor Ativado por Toque (llSensor)**

Este script demonstra a utilização clássica da função llSensor para detetar avatares próximos quando o objeto é tocado.

● **Código:**

Snippet de código

// Script de Sensor Básico Ativado por Toque

// Baseado em exemplos de wiki.secondlife.com e lslwiki.digiworldz.com

default // Estado inicial e único do script.

{

touch_start(integer total_number) // Evento disparado quando um avatar toca o objeto.

// 'total_number' indica quantos avatares tocaram (geralmente 1).

{

// Inicia uma varredura única do sensor.

llSensor(

"", // name: String vazia deteta qualquer nome.

NULL_KEY, // id: NULL_KEY deteta qualquer avatar (UUID).

AGENT, // type: Flag AGENT (0x1) para detetar apenas avatares.

20.0, // radius: Raio de deteção em metros (ex: 20 metros).

PI // arc: Ângulo de varredura em radianos (PI = 3.14159... = 180 graus = esfera completa).

);

llOwnerSay("Sensor ativado. Procurando avatares num raio de 20m...");

}

sensor( integer detected ) // Evento disparado quando o sensor conclui a varredura e deteta algo.

// 'detected' é o número de avatares detetados.

{

llOwnerSay((string)detected + " avatar(es) detetado(s):"); // Informa o

proprietário quantos foram detetados.

integer i = 0; // Inicializa um contador para o loop.

while(i < detected) // Loop que itera por cada avatar detetado.

{

string avatarName = llDetectedName(i); // Obtém o nome do avatar no índice 'i'. key avatarKey = llDetectedKey(i); // Obtém a key (UUID) do avatar no índice 'i'. vector avatarPos = llDetectedPos(i); // Obtém a posição do avatar no índice 'i'.

// Envia uma mensagem ao proprietário com os detalhes do avatar detetado. llOwnerSay(" - Nome: " + avatarName + ", Key: " + (string)avatarKey + ", Posição: " + (string)avatarPos);

i++; // Incrementa o contador.

}

}

no_sensor() // Evento disparado se a varredura do sensor não detetar nenhum avatar.

{

llOwnerSay("Nenhum avatar detetado nas proximidades."); // Informa o

proprietário.

}

}

● **Explicação:**

○ O evento touch_start é o gatilho inicial. Quando o objeto é tocado, ele chama a função llSensor.13

○ A função llSensor realiza uma única varredura. Os seus parâmetros definem o que procurar e onde:

■ name (string): Filtra pelo nome legado do avatar ou objeto. Uma string vazia ("") funciona como um curinga para qualquer nome.13

■ id (key): Filtra pela chave UUID do avatar ou objeto. NULL_KEY funciona como um curinga para qualquer chave.13

■ type (integer): Uma máscara de bits que especifica o tipo de entidade a detetar. AGENT (valor 0x1) deteta avatares. Outras flags comuns incluem ACTIVE (objetos físicos), PASSIVE (objetos não-físicos), e SCRIPTED (objetos com scripts ativos). Múltiplos tipos podem ser combinados com o operador | (OU bitwise).13

■ radius (float): A distância máxima de deteção em metros, a partir do centro do objeto que contém o script. O alcance válido é de 0.0 a 96.0 metros.13

■ arc (float): O ângulo máximo (em radianos) do cone de deteção, medido a partir do eixo X positivo local do objeto. PI (aproximadamente 3.14159) representa uma varredura esférica completa (180 graus em relação ao eixo, 360 graus total). PI/2 representa um hemisfério (90 graus), e PI/4 um cone de 45 graus.13

○ Após a conclusão da varredura, um de dois eventos é acionado: sensor se algo for detetado, ou no_sensor caso contrário.13

○ O manipulador sensor(integer detected) recebe o número de entidades detetadas. Um loop (while ou for) é então usado para processar cada

deteção. Funções como llDetectedName(index), llDetectedKey(index), e llDetectedPos(index) recuperam informações sobre a entidade detetada no índice especificado (de 0 a detected - 1).13

○ Existem algumas limitações importantes para llSensor:

■ **Contagem Máxima:** Originalmente limitado a 16 deteções por varredura, este limite foi aumentado para 32 numa atualização recente (Março de 2024).13

■ **Alcance:** Limitado a um raio máximo de 96.0 metros.13

■ **Limites de Região:** Não consegue detetar objetos ou avatares através das fronteiras entre regiões (sims).13

■ **Auto-Deteção/Anexos:** Objetos não se detetam a si mesmos, e anexos não podem detetar o avatar que os veste. Sensores também não detetam prims filhos dentro do mesmo objeto linkado.13

○ Para varreduras contínuas, llSensorRepeat é mais eficiente do que chamar llSensor repetidamente dentro de um evento timer. llSensorRemove é usado para parar um sensor repetitivo.13

● **Considerações sobre llSensor:** A função llSensor oferece uma forma direta de implementar deteção baseada em proximidade e tipo, com filtros incorporados nos seus parâmetros. Contudo, as suas limitações intrínsecas de alcance e contagem de deteções derivam provavelmente de considerações de desempenho do simulador, que precisa realizar uma consulta espacial ativa para cada

chamada. Esta abordagem é adequada para gatilhos localizados simples, como detetores de proximidade para portas ou armadilhas, mas torna-se insuficiente para sistemas de radar mais complexos, monitorização de áreas extensas ou cenários com muitos avatares, especialmente perto das fronteiras da região.

**2.3. Exemplo 2: Scanner de Região (llGetAgentList) com Filtragem de Alcance**

Uma abordagem mais moderna e frequentemente preferida para deteção de avatares em áreas maiores ou para um número maior de avatares envolve llGetAgentList.

● **Código:**

Snippet de código

// Script de Scanner de Região com Filtro de Distância

// Utiliza llGetAgentList para obter todos os avatares na região

// e depois filtra por distância.

float DETECT_RADIUS = 60.0; // Raio de deteção desejado em metros.

integer SCAN_INTERVAL = 5; // Intervalo entre varreduras em segundos.

list gAvatarsInRangeKeys =; // Lista para armazenar as keys dos avatares dentro do raio.

list gAvatarsInRangeNames =; // Lista para armazenar os nomes dos avatares dentro do raio.

default

{

state_entry()

{

llOwnerSay("Scanner de região ativado. Verificando avatares a cada " +

(string)SCAN_INTERVAL + " segundos num raio de " + (string)DETECT_RADIUS + "m."); llSetTimerEvent(SCAN_INTERVAL); // Inicia o temporizador para varreduras periódicas.

}

timer()

{

// Obtém a lista de keys de todos os avatares na região.

list allAgents = llGetAgentList(AGENT_LIST_REGION,);

// Limpa as listas de resultados anteriores.

gAvatarsInRangeKeys =;

gAvatarsInRangeNames =;

integer i; // Contador para o loop.

integer count = llGetListLength(allAgents); // Número total de avatares na região. vector myPos = llGetPos(); // Obtém a posição deste objeto uma vez para eficiência.

// Itera sobre cada key na lista de todos os agentes.

for (i = 0; i < count; i++)

{

key agentKey = llList2Key(allAgents, i); // Extrai a key do agente atual.

// Obtém detalhes do agente (posição e nome).

// OBJECT_POS retorna a posição. OBJECT_NAME retorna o nome.

list agentDetails = llGetObjectDetails(agentKey,);

// Verifica se a lista de detalhes não está vazia (agente ainda está na região). if (llGetListLength(agentDetails) > 0)

{

vector agentPos = llList2Vector(agentDetails, 0); // Extrai a posição do agente.

string agentName = llList2String(agentDetails, 1); // Extrai o nome do agente.

// Calcula a distância entre este objeto e o agente.

float distance = llVecDist(myPos, agentPos);

// Se o agente estiver dentro do raio de deteção definido...

if (distance < DETECT_RADIUS)

{

// Adiciona a key e o nome do agente às listas de resultados.

gAvatarsInRangeKeys += [agentKey];

gAvatarsInRangeNames += [agentName];

}

}

}

// Informa o proprietário sobre os resultados.

integer numFound = llGetListLength(gAvatarsInRangeKeys);

if (numFound > 0)

{

llOwnerSay("Avatares dentro de " + (string)DETECT_RADIUS + "m (" +

(string)numFound + "): " + llList2CSV(gAvatarsInRangeNames));

// Aqui, você poderia usar as listas gAvatarsInRangeKeys e

gAvatarsInRangeNames

// para outras ações, como exibir um menu de diálogo (llDialog).

}

else

{

llOwnerSay("Nenhum avatar encontrado dentro de " + (string)DETECT_RADIUS + "m.");

}

}

changed(integer change)

{

// Se o script for reiniciado ou o proprietário mudar, reinicia o temporizador. if (change & (CHANGED_OWNER | CHANGED_INVENTORY))

{

llResetScript();

}

}

}

● **Explicação:**

○ A função llGetAgentList(AGENT_LIST_REGION,) é chamada, geralmente dentro de um evento timer para varreduras periódicas. AGENT_LIST_REGION

especifica que queremos todos os avatares na região atual. A função retorna uma list contendo as key (UUIDs) de todos os avatares presentes.15

○ O script então itera sobre esta lista de chaves.15

○ Para cada chave de avatar, llGetObjectDetails(agentKey,) é usado para obter a posição (OBJECT_POS) e o nome (OBJECT_NAME) do avatar. Esta função retorna uma lista com os detalhes solicitados.15

○ A distância entre a posição do objeto do script (llGetPos()) e a posição do avatar é calculada usando llVecDist().15

○ Se a distância calculada for menor que o raio desejado (ex: 60.0 metros), a chave e/ou nome do avatar são adicionados a uma nova lista filtrada.15 ○ As vantagens desta abordagem são significativas: não há limite de alcance dentro da região e o limite de deteção é muito maior (acima de 100

avatares).15

● **Mudança de Paradigma de Desempenho:** A comunidade de scripting do Second Life considera cada vez mais llGetAgentList como a abordagem superior

e mais rápida para aplicações do tipo radar em comparação com llSensor.15 A razão subjacente parece ser que llGetAgentList acede a uma lista interna de agentes já mantida pelo simulador - uma operação de consulta relativamente direta. Em contraste, llSensor executa uma consulta espacial ativa a cada chamada, o que pode envolver a verificação de muitos objetos dentro do volume de varredura e ser computacionalmente mais intensivo, especialmente para varreduras amplas ou em áreas densamente povoadas. Embora a filtragem manual por distância em LSL após llGetAgentList adicione alguma sobrecarga ao script, a recuperação inicial dos dados é muito mais eficiente. Portanto, para aplicações que necessitam de atualizações frequentes sobre a presença de avatares em áreas maiores ou com maior densidade populacional, llGetAgentList é a metodologia preferida atualmente.

**3. Scripts de Sistemas de Teleporte**

**3.1. Introdução ao Teleporte LSL**

O teleporte programado é uma ferramenta poderosa no Second Life, permitindo mover avatares instantaneamente entre locais. Contudo, esta funcionalidade está sujeita a restrições de permissão significativas, especialmente quando se tenta teleportar avatares que não são os proprietários do objeto que contém o script.8 A função llTeleportAgent só pode teleportar o proprietário do objeto, a menos que o script faça parte de uma Experiência autorizada pelo usuário.8

**3.2. Exemplo 1: HUD de Teleporte Baseado em Landmarks**

Um Heads-Up Display (HUD) é um objeto anexado à tela do usuário. Este exemplo mostra um HUD que permite ao proprietário teleportar-se para landmarks armazenados no seu inventário.

● **Código:**

// Requer 9 prims linkados: 1 root (display) e 8 botões (tp1 a tp8).

key owner; // Armazena a key do proprietário do HUD.

● **Explicação:**

○ O HUD é construído a partir de múltiplos prims linkados, onde o prim raiz serve como botão principal e os prims filhos (nomeados tp1 a tp8) atuam como botões para os landmarks.7

○ A função toggle() controla a visibilidade dos botões filhos, usando

llSetLinkPrimitiveParamsFast para alterar a sua posição, tamanho, cor, transparência (alpha) e texto.7 Quando visíveis, os botões exibem os nomes dos landmarks correspondentes, obtidos com

llGetInventoryName(INVENTORY_LANDMARK, index).7

○ O evento touch_start deteta qual prim foi tocado (llDetectedLinkNumber, llGetLinkName). Se o prim raiz for tocado, ele alterna a visibilidade do menu (toggle()). Se um botão de landmark for tocado, o nome do landmark

correspondente é recuperado.7

○ A função llTeleportAgent(owner, landmarkName, ZERO_VECTOR,

ZERO_VECTOR) é chamada para teleportar o proprietário (owner) para o landmark selecionado (landmarkName).7 Os ZERO_VECTORs indicam que não há uma posição de aterragem específica ou um ponto para onde olhar após o teleporte.

○ O script solicita PERMISSION_TELEPORT usando llRequestPermissions. A concessão desta permissão é verificada no evento run_time_permissions e armazena o estado na flag gotTPperms.7

○ O "hack de área sem script" envolve solicitar PERMISSION_TAKE_CONTROLS e usar llTakeControls. Embora o evento control esteja vazio, ter controle ativo pode, em algumas circunstâncias, permitir que o HUD funcione mesmo em parcelas que proíbem scripts.7

**3.3. Exemplo 2: HUD de Teleporte para Posição da Câmera**

Este tipo de HUD permite ao usuário teleportar-se para onde a sua câmera está

apontada.

● **Código:**

Snippet de código

**3.5. Outros Conceitos de Teleporte**

● **Portais de Passagem:** Criar portais que teleportam automaticamente um avatar quando ele passa por eles geralmente requer o uso de Experiências para obter permissão implícita de teleporte (llTeleportAgent) ou soluções alternativas complexas envolvendo HUDs anexados que detetam a passagem e realizam o teleporte.10

Clicar neste link abre o mapa para o usuário confirmar o teleporte.8

**4.1. Introdução a Portas Scriptadas**

**4.5. Outros Métodos de Controlo de Acesso**

Além de senhas e listas de UUIDs, existem outras formas de controlar o acesso a portas:

● **Chaves Anexadas:** Pode-se verificar se um avatar está a usar um objeto específico (uma "chave"). Isto pode ser feito obtendo a lista de anexos do avatar com llGetAttachedList(avatarKey) e depois iterando sobre essa lista para verificar o nome ou, de forma mais segura, um identificador único do objeto chave. Um método robusto para identificar unicamente um objeto é usar o seu tempo de criação, obtido com llGetObjectDetails(key,). O script da porta armazenaria o tempo de criação da chave "mestra", e ao verificar os anexos de um avatar, compararia o tempo de criação de cada anexo com o valor armazenado.22 ● **Comunicação Chave-Porta:** Uma chave anexada pode conter um script que comunica com a porta. Por exemplo, a chave poderia usar llWhisper num canal secreto quando anexada, e a porta usaria llListen nesse canal para detetar a presença da chave nas proximidades.22

● **Complexidade da Configuração:** A necessidade de configurar portas com precisão (posições abertas/fechadas) apresenta um desafio de usabilidade. Métodos como gravar estados via chat 18 ou exigir nomes e linkagem específicos 21 são soluções comuns, mas podem ser complexos para usuários finais.

Armazenar a configuração no nome/descrição do objeto 18 é uma técnica LSL comum para persistir dados sem edição direta do script, mas requer que o

usuário siga instruções precisas. Um design de script de porta bem-sucedido deve incluir um mecanismo de configuração claro e o mais simples possível para garantir que os usuários possam instalar e usar a porta corretamente.

**5. Scripts de Controlo de Luz**

**5.1. Introdução à Iluminação LSL**

Objetos no Second Life podem ser transformados em fontes de luz através da manipulação dos seus parâmetros de primitiva.23 As propriedades chave que definem uma fonte de luz LSL são:

● **Estado Ligado/Desligado:** Controlado pelo parâmetro booleano associado a PRIM_POINT_LIGHT. TRUE ativa a luz, FALSE desativa.23

● **Cor:** Definida por um vector RGB (Red, Green, Blue) associado a

PRIM_POINT_LIGHT, com valores de 0.0 a 1.0 para cada componente.23

● **Intensidade:** Um valor float (0.0 a 1.0) que determina o brilho absoluto da luz.23 ● **Raio (Radius):** Um float (em metros) que define a distância que a luz percorre antes de se dissipar na iluminação ambiente.23

● **Falloff:** Um float (0.01 a 2.0) que controla a rapidez com que a intensidade da luz diminui com a distância. Valores mais altos significam uma queda mais abrupta.23

É importante notar que o sistema de renderização do Second Life tem um limite no número de fontes de luz dinâmicas que pode processar simultaneamente numa cena (historicamente 6, excluindo sol/lua, embora possa variar com as configurações do visualizador).23

**5.2. Exemplo 1: Interruptor de Luz Básico (Toggle)**

Este é o tipo mais comum de script de luz, onde tocar no objeto alterna o estado da luz entre ligado e desligado.

● **Código:**

Snippet de código

// Script de Interruptor de Luz Básico (Toggle on Touch)

// Baseado em exemplos de [23] e [25]

// --- Configurações da Luz ---

vector LIGHT_COLOR = <1.0, 1.0, 0.8>; // Cor da luz (Branco ligeiramente amarelado)float LIGHT_INTENSITY = 1.0; // Intensidade máxima (0.0 a 1.0)

float LIGHT_RADIUS = 10.0; // Alcance da luz em metros (0.1 a 20.0)

float LIGHT_FALLOFF = 0.5; // Queda da intensidade (0.01 a 2.0)

float GLOW_AMOUNT = 0.2; // Intensidade do brilho do objeto (0.0 a 1.0)integer START_ON = FALSE; // TRUE para começar ligado, FALSE para começar desligado

// --- Variáveis Internas ---

integer isLightOn; // Armazena o estado atual da luz (TRUE/FALSE ou 1/0)

// Função para ligar/desligar a luz e atualizar a aparência.

ToggleLight()

{

isLightOn =!isLightOn; // Inverte o estado atual (liga se estava desligado, desliga se estava ligado).

if (isLightOn) // Se a luz deve ser LIGADA.

{

llOwnerSay("Luz Ligada.");

llSetPrimitiveParams();

// Opcional: Mudar a cor do objeto para indicar que está ligado.

// llSetColor(LIGHT_COLOR, ALL_SIDES);

}

else // Se a luz deve ser DESLIGADA.

{

llOwnerSay("Luz Desligada.");

llSetPrimitiveParams();

// Opcional: Restaurar a cor original do objeto.

// llSetColor(<1.0, 1.0, 1.0>, ALL_SIDES); // Ex: Branco

}

}

default

{

state_entry()

{

// Define o estado inicial baseado na configuração START_ON.

// Coloca!START_ON para que a primeira chamada a ToggleLight() defina o estado

correto.

isLightOn =!START_ON;

ToggleLight(); // Chama a função para definir o estado inicial.

llSetText("Tocar para\nLigar/Desligar", <1.0,1.0,1.0>, 1.0); // Texto flutuante. }

touch_start(integer total_number)

{

// Ao ser tocado, chama a função para alternar o estado da luz.

ToggleLight();

}

changed(integer change)

{

// Se o proprietário mudar, reinicia o script.

if (change & CHANGED_OWNER)

{

llResetScript();

}

}

}

● **Explicação:**

○ Uma variável global, geralmente um integer (isLightOn ou on_off), é usada para armazenar o estado atual da luz (TRUE/1 para ligado, FALSE/0 para desligado).23

○ O evento touch_start é o gatilho. Quando o objeto é tocado, a lógica de alternância é executada.23

○ A alternância é tipicamente feita invertendo o valor da variável de estado: isLightOn =!isLightOn;.23 O operador ! (NÃO lógico) converte TRUE para FALSE e vice-versa.

○ A função llSetPrimitiveParams é usada para aplicar as mudanças. O parâmetro chave é PRIM_POINT_LIGHT, que recebe cinco valores

subsequentes: o estado booleano (isLightOn), a cor (vector), a intensidade (float), o raio (float) e o falloff (float).23

○ Frequentemente, PRIM_GLOW (para fazer o próprio objeto brilhar) e PRIM_FULLBRIGHT (para fazer o objeto ignorar sombras) também são definidos em sincronia com o estado da luz para melhorar o efeito visual.23

**5.3. Exemplo 2: Controlo de Luz num Prim Filho**

É comum ter um objeto (como um interruptor) que controla a luz emitida por outro objeto (como uma lâmpada) dentro do mesmo conjunto linkado.

○ O conceito chave é usar llSetLinkPrimitiveParams ou a sua versão mais rápida llSetLinkPrimitiveParamsFast.26 Estas funções permitem modificar os

● **Sincronização Visual:** É comum que scripts de luz ajustem não apenas a

emissão de luz (PRIM_POINT_LIGHT), mas também a aparência do próprio objeto emissor, como o brilho (PRIM_GLOW), a luminosidade total (PRIM_FULLBRIGHT) e, por vezes, a cor (llSetColor).23 Isto ocorre porque a fonte de luz LSL ilumina o

ambiente, mas não altera inerentemente a aparência do objeto que a contém. Sincronizar estes parâmetros visuais com o estado ligado/desligado da luz cria uma representação visual mais convincente e intuitiva para o usuário (por exemplo, a lâmpada parece acesa e brilhante quando a luz está ativa).

**6. Scripts de Distribuidores de Inventário (Givers)**

**6.1. Introdução à Distribuição Scriptada**

Distribuidores (Givers) são objetos que entregam itens do seu próprio inventário para o inventário de um avatar, geralmente quando tocados. As funções LSL primárias para esta tarefa são llGiveInventory (para um único item) e llGiveInventoryList (para múltiplos itens, opcionalmente numa pasta).28 A capacidade de dar um item depende crucialmente das permissões desse item no inventário do objeto distribuidor;

geralmente, o proprietário do objeto deve ter permissão de cópia (PERM_COPY) ou transferência (PERM_TRANSFER) sobre o item.11 É importante notar que pastas, como vistas no inventário do usuário, não podem ser colocadas diretamente dentro do inventário de um objeto; apenas os itens individuais podem.28
